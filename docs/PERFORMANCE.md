## المنهجية

استُخدم `k6/all.js` والـdataset نفسه ومراحل التحميل نفسها في ثلاث تشغيلات مستقلة، مع warm-up مدته 30 ثانية قبل القياس. يصل الحمل إلى 100 VU إجمالًا: 40 لقراءة المنتجات، و20 لكل من تفاصيل المنتج وقراءة الطلبات وإنشاء الطلب. مجموع الـstages أربع دقائق، والعملية الكاملة نحو 4:15 مع تسجيل الدخول في `setup`. جرى تنفيذ `ANALYZE VERBOSE` على جداول قاعدة `ecommerce_db` قبل baseline، وحُفظت حالة الشيفرة في `results/baseline-code-state.txt`.

أُطفئ عدّاد Prisma في warm-up وتشغيلات latency لتجنب تأثير التسجيل على p95. جُمعت المقاييس الرقمية بوسيط التشغيلات الثلاث في `results/baseline.json`. يوضح جدول التشغيلات تفاوتًا كبيرًا في التشغيل الأول، لذلك يجب قراءة الوسيط مع نطاق التشغيلات الخام وعدم إخفاء هذا التفاوت.

احتوى warm-up على 507 طلبات وفشل واحد (0.197%). سيناريو `POST /orders` يكتب طلبات فعلية أثناء كل تشغيل؛ استُخدم حساب منفصل للكتابة، لذلك تتغير بيانات هذا الحساب قليلًا بين التشغيلات ولا تُعاد قاعدة البيانات إلى حالتها السابقة.

## قياس ما بعد فهرس قاعدة البيانات

تشغيل k6 واحد بنفس `k6/all.js` والـstages والبيانات بعد إضافة فهرس `order_items.orderId`. هذا قياس منفرد مقابل وسيط ثلاثة تشغيلات baseline، لذلك تُقرأ المقارنة كمؤشر أولي لا كاختبار إحصائي مكرر. سجّل التشغيل 53,674 طلبًا، 220.584 طلبًا/ثانية، ونسبة فشل HTTP واحدة من 53,674 (0.0019%). لم تظهر مؤشرات 429 أو `TOO_MANY_REQUESTS` في سجلات backend التي فُحصت. تجاوزت `POST /orders` عتبة p95 البالغة 800ms؛ نتيجة `GET /products/:id` عند p99 أعلى من baseline، رغم تحسن p50 وp95.

## طبقة قاعدة البيانات

### تدقيق N+1 وخطة ما قبل الفهرس

| المسار | عمليات Prisma لكل طلب | التدقيق |
|---|---:|---|
| `GET /orders` | 2 | `findMany(include: { items: true })` و`count` فقط؛ العلاقة تُطلب ضمن قراءة الصفحة المجمعة، ولا توجد قراءة عناصر داخل حلقة التطبيق. |
| `GET /products` | 2 | `findMany(include: { category: true })` و`count`؛ جلب المخزون يتم بطلب `getStocks` مجمّع. |
| `GET /products/:id` | 1 | قراءة المنتج والعلاقة، ثم المخزون عبر `getStock`؛ لا يوجد تكرار لقراءة قاعدة البيانات لكل عنصر. |
| `POST /orders` | 1 | الكتابة ضمن transaction؛ عمليات الخدمات الداخلية سياقات HTTP منفصلة ولا تدخل في عدّ الطلب الخارجي. |

العداد يقيس عمليات Prisma داخل سياق HTTP وليس كل عبارة SQL داخل Prisma أو الخدمات الداخلية. خطة قراءة صفحة الطلبات تستخدم بالفعل `orders_userId_createdAt_idx` (20 صفًا في 0.181ms في عينة الخطة)، وعدّ الطلبات يستخدم الفهرس نفسه (8.306ms). أما قراءة العناصر المرتبطة بالصفحة، فقد فحصت تسلسليًا 902,603 من أصل نحو 903,068 صفًا في `order_items` واستغرقت 216.038ms، لأن الجدول لم يكن يملك فهرسًا على `orderId`. هذه هي مشكلة قاعدة البيانات المثبتة التي تعالجها migration المرحلة.

خطة بحث المنتجات استخدمت فهرس الفئة ثم صفّت 2,503 صفوف بشرط `ILIKE '%searchterm42%'` (16.563ms لقراءة الصفحة و3.260ms للعدّ في هذه العينة). لم يُضف فهرس بحث منفصل لأن هذه الخطة لم تثبت أنه عنق الزجاجة الأساسي مقارنةً بمسح عناصر الطلبات.

فهرس B-tree على `order_items.orderId` معرف في [مخطط Prisma](../prisma/orders/schema.prisma) وmigration [20261112000000_add_order_items_order_id_idx](../prisma/orders/migrations/20261112000000_add_order_items_order_id_idx/migration.sql)، وطُبّق قبل قياس ما بعد الفهرس. الخطط محفوظة في [explain-before.txt](./perf/explain-before.txt) و[explain-after.txt](./perf/explain-after.txt)، واستعلام إعادة القياس في [explain-after.sql](./perf/explain-after.sql).

## طبقة Read Replica

تنفيذ المرحلة الرابعة جاهز، لكن القياس لم يكتمل بعد. تتضمن [تعليمات Read Replica](./perf/PHASE4-READ-REPLICA.md) إعداد الـphysical standby، اختبار انتشار الكتابة، وتشغيلات control وreplica المتطابقة. ستضاف المقارنة وقياسات lag إلى هذا التقرير بعد اكتمال التشغيلات اليدوية؛ لا تُعد نتائج الأداء مؤكدة قبل ذلك.

## طبقة Redis

تُضاف سياسة TTL والإبطال ومعدل الإصابة ونتائج حماية cache stampede عند اكتمال المرحلة الخامسة.

## طبقة HTTP ETag

تُضاف نتائج 304 وحجم البيانات الموفرة بعد اكتمال المرحلة السادسة.
