# 📖 دليل استخدام Swagger — خطوة بخطوة

> هذا الدليل مكتوب لفريق المشروع (باك إند + فرونت إند) ليفهموا كيف يختبرون كل endpoint في المشروع.
> رابط السويغر بعد تشغيل السيرفر: **http://localhost:3000/api/docs**

---

## 1) ما هي Swagger أصلاً؟

Swagger UI هي صفحة ويب **تولّدها السيرفر تلقائياً** من كود الباك إند، تعرض:

- كل الـ endpoints المتاحة (المسارات) مع نوع كل واحدة (GET / POST / PUT / DELETE).
- شكل الـ body المطلوب لكل endpoint مع أمثلة جاهزة.
- شكل الـ response الذي ستحصل عليه (النجاح وكل أكواد الخطأ).
- **زر تجربة حقيقي**: تستطيع إرسال طلب فعلي إلى السيرفر ورؤية الرد الحقيقي — بدون Postman وبدون فرونت إند!

بمعنى: السويغر = **وثائق حية + أداة اختبار** في نفس الصفحة.

---

## 2) كيف أفتحها؟

```bash
# من داخل مجلد الباك إند
npm run start:dev
```

ثم افتح المتصفح على:

```
http://localhost:3000/api/docs
```

## 3) جولة في شاشة السويغر

| العنصر على الشاشة | ما هو؟ |
|---|---|
| **العنوان الأخضر في الأعلى** | اسم المشروع + الإصدار + رابط السيرفر (Server) |
| **وصف طويل** | شرح شكل الردود الموحد، طريقة التوثيق، الحسابات التجريبية، معاني أكواد الرد |
| **🔒 Authorize (زر أخضر أعلى اليمين)** | لصق التوكن JWT — مرة واحدة فقط وكل endpoint المحمية تصبح مفتوحة |
| **مجموعات الـ tags** | `auth` (التسجيل والدخول) و `users` (إدارة المستخدمين) و `health` |
| **اللون الأزرق/الأخضر/البرتقالي/الأحمر** | GET أزرق، POST أخضر، PUT برتقالي، DELETE أحمر |
| **صندوق Filter** | صندوق بحث أعلى الصفحة لتصفية الـ endpoints بكتابة كلمة |
| **مدة الطلب** | بعد كل Execute تظهر مدة الطلب بالمللي ثانية بجانب كود الرد |

---

## 4) الخطوات الأساسية لتجربة أي endpoint

1. اضغط على اسم الـ endpoint ليتمدد ويظهر التفاصيل.
2. اضغط زر **Try it out** (برتقالي) — يفتح حقول التعديل.
3. عدّل الـ **Request body** (يأتي معبأ بمثال جاهز — عدّل القيم فقط).
4. اضغط **Execute** الأزرق الكبير.
5. انزل لأسفل إلى **Server response**:
   - **Code**: كود الرد (200 = نجاح، 400/401/403... = خطأ).
   - **Response body**: جسم الرد الفعلي.
6. لإعادة التجربة بقيم أخرى: عدّل الـ body واضغط Execute مرة أخرى.

---

## 5) التوثيق (Authorize) — أهم خطوة على الإطلاق

معظم الـ endpoints محمية: لا تعمل إلا بـ **توكن JWT**. الطريقة:

### الخطوة أ: احصل على توكن
جرّب `POST /auth/login` بحساب جاهز (انظر الجلسة أدناه) — الرد سيكون:

```json
{
  "success": true,
  "data": {
    "accessToken": "eyJhbGciOiJIUzI1NiIs...",
    "user": { "id": "...", "email": "admin@restaurant.com", "role": "ADMIN" }
  },
  "timestamp": "..."
}
```

### الخطوة ب: الصق التوكن
1. انسخ قيمة `accessToken` **كاملة** (اضغط Copy بجانب الرد).
2. اضغط زر **🔒 Authorize** الأخضر أعلى اليمين.
3. الصق التوكن في الحقل (**بدون** كلمة Bearer — السويغر يضيفها تلقائياً).
4. اضغط **Authorize** ثم **Close**.

✅ الآن أي endpoint تحاولها سيرسل التوكن تلقائياً.
🔁 التوكن يبقى محفوظاً حتى بعد تحديث الصفحة (`persistAuthorization`) — وعندما تنتهي صلاحيته تعيد الدخول.

## 7) 🧪 جلسة اختبار كاملة — نفّذها بالترتيب

نفّذ هذه الخطوات في السويغر بالترتيب من 1 إلى 10. هذه نفس الجلسة التي ستشرحها لفريق الفرونت.

### الخطوة 1 — GET /health (فحص السيرفر)
- Try it out → Execute.
- ✅ المتوقع: `200` و `data.status: "ok"`.
- معناها: السيرفر شغّال والاتصال سليم.

### الخطوة 2 — POST /auth/login (دخول الأدمن)
- Body جاهز داخل السويغر — اختر مثال **"Admin (email)"**:

```json
{ "identifier": "admin@restaurant.com", "password": "Admin@123" }
```

- ✅ المتوقع: `200` + `data.accessToken` + `data.user.role: "ADMIN"`.
- ⚠️ جرّب أيضاً مثال **"Admin (username)"** (`identifier: "admin"`) — نفس النتيجة.
- انسخ التوكن الآن.

### الخطوة 3 — Authorize 🔒
- الصق التوكن (كما في القسم 5 أعلاه).

### الخطوة 4 — GET /auth/me (من أنا؟)
- Execute بدون أي مدخلات.
- ✅ المتوقع: `200` وبيانات الأدمن نفسه.
- 💡 هذه هي الطريقة التي سيتحقق بها الفرونت عند فتح التطبيق: 200 = مستخدم مسجل دخول، 401 = حوّله لصفحة الدخول.

### الخطوة 5 — POST /auth/register (تسجيل عميل جديد)

```json
{
  "email": "ahmad@example.com",
  "username": "ahmad",
  "password": "Ahmad@12345",
  "firstName": "Ahmad",
  "lastName": "Ali"
}
```

- ✅ المتوقع: `201` + توكن جديد + `role: "CUSTOMER"`.
- ⚠️ لاحظ: لا يوجد حقل `role` — كل من يسجل من هنا يصبح CUSTOMER تلقائياً.
- ⚠️ أعد الإرسال بنفس الإيميل → `409` Email already exists.
- أعد الخطوة 3 بتوكن الحساب الجديد إن أردت، أو عُد لتوكن الأدمن.

### الخطوة 6 — GET /users (قائمة المستخدمين — أدمن)
- Execute بدون تعديل (اختياري: جرّب `search=ahmad` أو `limit=5`).
- ✅ المتوقع: `200` + `data.items` (قائمة) + `data.meta` (total, page, totalPages...).

### الخطوة 7 — POST /users (إنشاء مستخدم — أدمن فقط)

```json
{
  "email": "manager@restaurant.com",
  "username": "manager",
  "password": "Manager@123",
  "firstName": "Store",
  "lastName": "Manager",
  "role": "ADMIN"
}
```

- ✅ المتوقع: `201` ومستخدم جديد بدور ADMIN.
- ⚠️ احذف `"role"` من الـ body وأعد الإرسال → يُنشأ CUSTOMER (الافتراضي).

### الخطوة 8 — PUT /users/:id (تعديل مستخدم)
- انسخ `id` أي مستخدم من نتيجة الخطوة 6 والصقه في حقل `id`.
- Body: عدّل حقلاً واحداً فقط (تعديل جزئي):

```json
{ "firstName": "UpdatedName" }
```

- أو لترقية مستخدم: `{ "role": "ADMIN" }` — أو لتعطيله: `{ "isActive": false }`.
- ✅ المتوقع: `200` والبيانات الجديدة.

### الخطوة 9 — DELETE /users/:id (حذف مستخدم)
- انسخ `id` مستخدم **ليس أنت** (مثلاً `manager`) والصقه.
- ✅ المتوقع: `200` و `{ "message": "User deleted successfully" }`.
- ⚠️ جرّب حذف **نفسك** (id الأدمن الحالي) → `400 You cannot delete your own account` (حماية من حذف آخر أدمن).

### الخطوة 10 — اختبار الصلاحيات (RBAC) — الأهم للفرونت
1. سجّل دخول بحساب **customer@test.com** (الخطوة 2) واعمل Authorize بتوكنه.
2. جرّب `GET /users` → ✅ المتوقع **`403 Forbidden`** — العميل ممنوع من إدارة المستخدمين.
3. جرّب `GET /users/profile` → ✅ المتوقع `200` — ملفه الشخصي مسموح لأي مستخدم.
4. جرّب `DELETE /users/:id` → `403`.

> **خلاصة الصلاحيات**: بدون توكن = 401 · بتوكن عميل على endpoint إدارية = 403 · بتوكن أدمن = 200.

## 8) جدول مرجعي سريع — كل الـ endpoints

| # | Method | المسار | توكن؟ | من يقدر يستدعيها؟ | الوظيفة |
|---|---|---|---|---|---|
| 1 | GET | `/health` | ❌ لا | الجميع | فحص أن السيرفر حي |
| 2 | POST | `/api/v1/auth/register` | ❌ لا | الجميع | إنشاء حساب عميل جديد (دائماً CUSTOMER) |
| 3 | POST | `/api/v1/auth/login` | ❌ لا | الجميع | تسجيل الدخول (إيميل أو اسم مستخدم) → توكن |
| 4 | GET | `/api/v1/auth/me` | ✅ JWT | أي مستخدم مسجل | بياناتي الحالية (فحص الجلسة) |
| 5 | POST | `/api/v1/users` | ✅ JWT | ADMIN فقط | إنشاء مستخدم (الطريقة الوحيدة لإنشاء ADMIN) |
| 6 | GET | `/api/v1/users` | ✅ JWT | ADMIN فقط | قائمة المستخدمين (صفحات + بحث) |
| 7 | GET | `/api/v1/users/profile` | ✅ JWT | أي مستخدم مسجل | ملفي الشخصي |
| 8 | GET | `/api/v1/users/:id` | ✅ JWT | ADMIN فقط | بيانات مستخدم محدد |
| 9 | PUT | `/api/v1/users/:id` | ✅ JWT | ADMIN فقط | تعديل مستخدم (جزئي) / تعطيل / ترقية |
| 10 | DELETE | `/api/v1/users/:id` | ✅ JWT | ADMIN فقط | حذف مستخدم (ممنوع حذف النفس) |

## 9) دليل أكواد الردود

| الكود | المعنى | مثال متى يحدث |
|---|---|---|
| **200** | نجاح | أي GET ناجح، login، تعديل، حذف |
| **201** | تم الإنشاء | register، POST /users |
| **400** | خطأ تحقق (validation) | إيميل غير صالح، كلمة مرور قصيرة — **`message` هنا مصفوفة** |
| **401** | لا توكن / توكن خاطئ / منتهي | نسيت Authorize أو التوكن انتهى |
| **403** | الدور لا يملك صلاحية | عميل حاول `GET /users`، أو حساب مقفول/معطل عند الدخول |
| **404** | غير موجود | id غير موجود في GET/PUT/DELETE |
| **409** | تعارض | إيميل أو username مستخدم مسبقاً |
| **429** | طلبات كثيرة | تجاوزت حد المعدل — انتظر قليلاً |

**شكل خطأ موحد** (نفس الشكل دائماً — ابنوا handler واحد في الفرونت):

```json
{
  "statusCode": 400,
  "message": ["email must be an email", "password must be longer than or equal to 8 characters"],
  "error": "Bad Request",
  "timestamp": "2026-10-27T12:00:00.000Z",
  "path": "/api/v1/auth/register"
}
```

## 10) أخطاء شائعة وحلولها

| المشكلة | السبب | الحل |
|---|---|---|
| كل الـ endpoints تعطي 401 | لم تضغط Authorize | سجّل دخول ثم الصق التوكن في 🔒 |
| 401 رغم أني عملت Authorize | التوكن انتهت صلاحيته أو نسخته ناقصاً | أعِد login وانسخ التوكن كاملاً |
| 403 على GET /users | سجّلت دخول بحساب CUSTOMER | استخدم حساب الأدمن |
| `message` مصفوفة أحياناً ونص أحياناً | 400 = مصفوفة، باقي الأخطاء = نص | وثّق هذا للفرونت (handler يتعامل مع الحالتين) |
| 429 أثناء التجربة | أرسلت طلبات كثيرة بسرعة | انتظر دقيقة، الحد per-IP |
| 403 عند login | 5 محاولات خاطئة → قفل 15 دقيقة | انتظر 15 دقيقة أو أعِد reset للداتابيز |
| Swagger لا يفتح | السيرفر غير شغّال أو البورت خطأ | `npm run start:dev` ثم تأكد من البورت 3000 |

## 11) ملاحظات للفرونت إند

1. **الغلاف الموحد**: كل نجاح = `{ success, data, timestamp }` — بياناتك الحقيقية داخل `data` دائماً.
2. **أخطاء 400**: `message` مصفوفة → اعرض كل العناصر.
3. **التوكن**: خزّنه وأرسله بكل طلب: `Authorization: Bearer <token>`.
4. **بعد فتح التطبيق**: نادِ `/auth/me` — إذا 200 استكمل الجلسة، إذا 401 وجه لصفحة الدخول.
5. **الترقيم**: استخدم `meta` من `GET /users` لبناء أزرار الصفحات (`hasNext` / `hasPrev` / `totalPages`).
6. انتهاء التوكن يعطي **401** → أعِد التوجيه لصفحة الدخول تلقائياً.
